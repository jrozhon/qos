# Lecture 08 — QoS architectures in IP networks: IntServ/RSVP and DiffServ

Design for a new deck `slides/08-qos-architectures.md` and a new interactive component
`slides/components/QosPathSim.vue`. Date: 2026-11-23.

## Intent

The course had an old Google-Slides lecture "10 - QoS in IP Networks" (`slides/10-diffserv.pdf`, 17 pages,
bullet-only: IntServ classes and TSpec/RSpec, an IntServ router block diagram, DiffServ edge/core, the
classifier→marker→meter→remarker/shaper/dropper chain, PHBs BE/AF/EF, the DSCP table, queue types FIFO/CQ/WFQ/
CBWFQ/PQ/LLQ, RED/WRED/CBWRED, and a teaser "DiffServ and OpenFlow?"). The lecturer wants it rebuilt as
lecture #8 in the Slidev series, in the same layout and visual identity as decks 01–07 and 09, building on
Lecture 03 rather than repeating it, enriched with material from well-known textbooks, RFCs and research, and with
a live visualisation of RSVP and DSCP as they traverse a network.

What students should take away (the lecturer chose "both" for the visualisation): the *mechanics* of each
architecture (RSVP messages hop by hop, admission per hop, soft state; DSCP marked at the edge, per-class queues in
the core) **and** the *scaling* argument that falls out of the mechanics (per-flow state in every RSVP router vs a
fixed handful of classes in a DiffServ core).

## Goals

- A 90-minute deck `08-qos-architectures.md` following the house rhythm (slides/README.md "Writing a new deck"):
  cover → where we are going → outcomes → thesis `statement` → `section` per part → content with checkpoints →
  common mix-ups → summary → exit questions → where you use this → references → `end` → Extras.
- One reusable component `QosPathSim.vue` with `mode="rsvp"` and `mode="diffserv"` on one shared topology and one
  shared state panel; a side-by-side "scale" slide using two instances.
- Static light/dark SVG figures for everything that is a diagram rather than a simulation, generated by a new
  `# 08` section of `scripts/generate-figures.py`.
- Content goes deeper than Lecture 03 and explicitly points back to it ("Lecture 03 introduced X; here…").
- PDF export works: the component draws a static, meaningful frame in print mode.

  `qos-05` Mininet/`tc` for trying queues and marking; `qos-03` for measuring the effect.)
- No full RSVP/DiffServ protocol simulator; the component is a teaching animation with simple, explicit rules.
- No vendor CLI deep-dive (Cisco MQC etc.); at most one short Linux `tc`/`ip` snippet, in `bash` fences.
- No rewrite of Lecture 03.

## Deck content (Part structure)

Timing target: 8 / 25 / 32 / 15 / 10 min (≈ 90). Titles are proposals; the builder may merge or split slides.

**Opening** — cover; "Where we are going" (4 parts grid with ↔ Lecture 03 links instead of lab steps);
outcomes (5); thesis statement: *"Guarantee needs state; scale forbids state — IntServ and DiffServ are the two
ends of that trade-off."*

**Part 1 — Why architecture, not just mechanisms** (bridge from Lecture 03)
- Recap in one slide: Lecture 03's toolbox (CAC, token bucket, WFQ, RED, DSCP) — "mechanisms in one box";
  this lecture is about making them work *end to end across many boxes*.
- Best effort is the default; two answers since the 1990s: reserve per flow (IntServ) or treat per class
  (DiffServ). Timeline figure redrawn (move/extend Lecture 03's Extras timeline: RFC 1633 → 2205 → 2474/2475 →
  2597/3246 → 2998 → 3209 → 4594 → 8622 → 9330–9332 L4S).
- Checkpoint: "Why can't each router just do its own QoS?" (answer: one un-configured hop with FIFO undoes it —
  the old PDF's "all network elements need to be capable").

**Part 2 — Integrated Services and RSVP**
- IntServ model (RFC 1633): per-flow guarantees, the four router components (reservation set-up agent,
  admission control, classifier, packet scheduler) — redrawn version of the old PDF's block diagram, control
  vs data plane.
- Service classes: Guaranteed (RFC 2212 — firm delay bound), Controlled-Load (RFC 2211 — "as an unloaded network"),
  best effort. TSpec as token bucket $(r, b, p, m, M)$ — explicitly Lecture 03's bucket; RSpec $(R, S)$.
- Guaranteed-service delay bound (fluid form): $D \le b/R$ (+ error terms $C/R + D$ per hop, shown, not derived),
  with a worked example: a voice aggregate with given $b$, $R$ → delay bound; links to Parekh–Gallager.
- RSVP (RFC 2205): receiver-initiated; PATH downstream stores previous hop + sender TSpec; RESV upstream with
  FlowSpec, admission at every hop; PathErr/ResvErr; **soft state** with refresh (default R = 30 s; state lifetime L ≥ (K + 0.5)·1.5·R with K = 3, i.e. ≈ 157 s —
  the slide states the RFC formula; K is the number of refreshes that may be lost); PathTear/ResvTear. Reservation styles (FF, SE, WF) in one table; multicast merging mentioned.
- **Live: `QosPathSim mode="rsvp"`** (one slide, plus a print frame).
- Why it didn't scale: state ∝ flows; refresh messages ∝ flows / 30 s; per-flow classification at line rate;
  inter-domain policy and billing. Back-of-envelope worked example (e.g. 100 k flows on a core link → state
  size and refresh message rate). RFC 2961 refresh reduction as the attempted fix.
- Where RSVP lives on: RSVP-TE for MPLS traffic engineering (RFC 3209), IntServ over DiffServ at the edge (RFC 2998),
  Voice-Admit (RFC 5865). Checkpoint on soft state ("a router reboots mid-call — what happens?").

**Part 3 — Differentiated Services**
- Architecture (RFC 2475): DS domain, boundary vs interior nodes, SLA/TCA, aggregates not flows; the Nichols–
  Jacobson–Zhang "two-bit" idea (RFC 2638) as the origin. Redrawn domain figure (edge vs core).
- Traffic conditioning block: classifier → meter → marker / shaper / dropper (old PDF slides 8–9), with
  what each does and where it runs (edge only).
- Meters: srTCM (RFC 2697: CIR, CBS, EBS) and trTCM (RFC 2698: CIR/PIR) — green/yellow/red → AFx1/x2/x3.
  Built on Lecture 03's token bucket: "two buckets instead of one". Worked example with a burst.
- The DSCP codepoint space: Lecture 03 showed the byte; here the pools and the full table — CS0–CS7,
  AF11–AF43 (class bits + drop-precedence bits, decimal and binary), EF 46, VOICE-ADMIT 44, LE 1 (RFC 8622).
  Redrawn table figure (replaces the old PDF's raster image). Small exercise: decode `0x88` ToS → DSCP 34 → AF41.
- PHBs: Default/BE; EF (RFC 3246 — low delay, low jitter, must be rate-limited at the edge, otherwise it starves
  everything); AF (RFC 2597 — 4 classes × 3 drop precedences, forwarding independence between classes,
  in-order within a class); CS for backward compatibility with IP Precedence; LE for scavenger traffic.
- Schedulers that realise PHBs: strict priority (EF), CBWFQ/DRR weights (AF classes), LLQ = PQ + CBWFQ;
  WRED per drop precedence inside an AF queue (drop curves per colour — extends Lecture 03's RED figure).
  Old PDF's CQ/WFQ/CBWFQ list condensed into one comparison table.
- RFC 4594 service-class table (telephony EF, signalling CS5, multimedia conferencing AF4x, real-time
  interactive CS4, multimedia streaming AF3x, broadcast video CS3, low-latency data AF2x, OAM CS2, high-throughput
  data AF1x, standard CS0, low-priority data LE) — ties to Lecture 05 (voice) and Lecture 07 (streaming).
- **Live: `QosPathSim mode="diffserv"`**.
- Checkpoints: "everything marked EF" (EF starvation / why edge policing is mandatory); "AF12 vs AF21 —
  which is dropped first?" (trick: different classes, drop precedence only compares within a class).

**Part 4 — IntServ vs DiffServ, and DSCP in the real Internet**
- **Live: two `QosPathSim` side by side, flows slider shared** — the scaling slide.
- Comparison table: granularity, state, signalling, guarantee type (absolute vs relative), scalability,
  admission, deployment (where you meet each today).
- DSCP across domain boundaries: re-marking/bleaching at peering points; measurement studies show a large
  share of Internet paths change or zero the DSCP (cite Custura, Fairhurst, Learmonth measurement work /
  RFC 9435); RFC 8100 interconnection classes; WebRTC marking RFC 8837; Wi-Fi WMM mapping (RFC 8325).
  Bell's "Failure to thrive" (2003) and Huston's RFC 2990 as the critical view of why inter-domain QoS stalled.
- Where QoS architecture went next (one slide, outlook): L4S (RFC 9330–9332, ECT(1) + DualQ — connects to
  Lecture 03's ECN), DetNet/TSN for bounded latency, 5G QoS flows with 5QI (per-flow again, inside one
  operator), SDN/OpenFlow meters and `set_field:ip_dscp` → Lecture 09.
- Common mix-ups (≥4): DSCP ≠ guarantee; EF ≠ "highest priority, unlimited"; AF drop precedence is intra-class;
  RSVP reserves nothing for the sender — the receiver requests; IntServ ≠ RSVP (RSVP is the signalling, also
  used without IntServ — RSVP-TE).
- Summary, exit questions (3–4), where you use this (`qos-05` Mininet with `tc` — `htb`/`prio` + DSCP filters;
  `qos-03` to measure the effect on voice), references (two slides: standards; literature), `end`.
- Extras (outside the 90 min): Guaranteed-service delay bound with $C$ and $D$ error terms; Core-Stateless Fair
  Queueing (Stoica & Zhang, SIGCOMM 1999) as the research attempt to get IntServ guarantees with DiffServ-like
  state; Linux `tc` snippet that classifies on DSCP.

## The interactive component — `QosPathSim.vue`

### Topology (shared by both modes) — two domains *(lecturer's decision)*

Horizontal chain across **two operators' domains**, fits 880 px (≈ 95 px node spacing):
`S` (sender host) — **Domain A:** `E1` (ingress edge) — `C1` — `C2` — `E2` (egress edge) ‖ peering link ‖
**Domain B:** `E3` (ingress edge) — `C3` — `E4` (egress edge) — `R` (receiver host).
Each domain has one **bottleneck** with a capacity shown as a fill bar: `C1→C2` in A (prop `capacityA`, default
10 \[Mbit/s\]) and `C3→E4` in B (prop `capacityB`, default 10 \[Mbit/s\]). Hosts are boxes, routers circles; edge
routers drawn in the "edge" style, core routers in the "core" style; each domain is a dashed rounded rectangle
labelled "Domain A" / "Domain B", the peering link between them is marked as the domain boundary. Under each
router: its **state panel** (same layout in both modes; in `compact` only counts).

### Shared controls and panel

- Play / Pause, **Step** (advance one event), Reset; speed slider.
- **Flows** control: "+1 flow", "+10 flows" and a flows slider (0–200 in side-by-side). Each flow gets a type
  drawn with a seeded RNG: voice (≈ 100 \[kbit/s\]), video (≈ 2 \[Mbit/s\]), data (best effort, elastic).
- Per-router **state table**: rows = entries that router keeps. Shows the count prominently ("12 entries") and
  the first ~5 rows, with "+ n more". Under the topology a small counter: signalling messages per second on the
  bottleneck (RSVP refreshes vs 0 for DiffServ).
- Seeded RNG (`seed` prop) so a lecture demo is reproducible.

### `mode="rsvp"`

- A new flow (voice or video; data flows are best effort and signal nothing) sends **PATH** S→E1→C1→C2→E2→R as a
  small labelled message; each hop adds a path-state row (flow id, previous hop, TSpec rate). R answers **RESV**
  hop by hop upstream; each hop runs admission: if the reserved sum on the outgoing link + request ≤ capacity →
  adds a reservation row (flow id, rate) and the bottleneck bar fills; otherwise the hop turns red, a **ResvErr**
  goes back to R, and the flow becomes best effort (shown in its colour/legend).
- **Refresh** toggle (default on): every refresh period (scaled animation time, e.g. 30 s → 3 s) each active
  reservation emits PATH/RESV refresh dots; the message-rate counter counts them. Turning refresh off lets
  state rows age (a fading timer per row) and expire after 3 missed refreshes — a simplification of RFC 2205's
  lifetime, stated on screen ("simplified: expires after 3 missed refreshes"); the bandwidth is released. A **"fail C1"**
  button (optional, builder's call) shows soft-state recovery: C1 loses its table, the next refresh rebuilds it.
- Once reserved, data packets of the flow are drawn travelling along the path in the flow's colour.
- RSVP crosses both domains: PATH/RESV and state rows appear in **every** router of A and B (all 7 routers keep
  per-flow state), admission at both bottlenecks; a refusal can come from either domain. A **"B refuses
  foreign reservations"** toggle (default off) makes E3 reject every RESV by policy (ResvErr with reason
  "policy"), illustrating why inter-domain IntServ never happened (Huston, RFC 2990).

### `mode="diffserv"`

- Flows send packets (no signalling). At **E1** the classifier assigns a DSCP by type (voice → EF 46, video →
  AF41 34, data → CS0) and an **srTCM/trTCM meter** per class re-marks out-of-profile video to AF42/AF43 (packet
  label changes visibly at E1). EF over its policed rate is dropped at E1 (FMT red).
- Each packet carries its DSCP label/colour through C1 and C2. Core routers show **per-class queues**: EF
  (strict priority), AF4 (weighted), BE — packets visibly join the queue matching their DSCP and are served by a
  simple PQ + weighted round robin scheduler at the bottleneck rate. Under overload: BE queue grows and drops;
  inside AF4, AF43 is dropped before AF42 before AF41 (WRED-like thresholds, simplified to fixed thresholds).
- Core state table = one row per class (EF, AF4x, BE, + CS6 network control greyed) regardless of flow count —
  the scaling point. E1's table, however, is per-flow (classifier rules/meters) — make that visible: "edge keeps
  per-flow state, core does not".
- **Domain boundary policy** selector at the E2→E3 peering (default "trust"): *trust* (DSCP kept),
  *re-mark* (Domain B maps per its own SLA, e.g. AF41 → AF31, EF kept only up to the agreed rate),
  *bleach* (all DSCP → 0). E3 is Domain B's classifier/policer and shows its own (per-SLA, not per-flow) rules.
  With *bleach*, voice packets visibly fall into Domain B's BE queue at C3 and suffer under B's congestion while
  they were protected in A — the slide's point about DSCP in the real Internet. Domain B's load is adjustable
  (a "cross-traffic in B" slider adding BE load on C3→E4) so the effect shows without touching A.

### Side-by-side (`compact` prop)

Two instances in a 2-column grid, `compact` hides the long text and per-row detail, keeps the topology, the
state counts per router and the bottleneck/signalling counters. One shared flows slider is not possible across
two components without a store; **builder's call**: either a `flows` prop driven by a slide-level `ref` in the
Markdown (`<script setup>` in the slide), or a wrapper component `QosCompare.vue` that hosts two `QosPathSim`
and one slider. Prefer the wrapper.

### Print mode

When `isPrintMode`, render a static frame: the topology with a fixed scenario (RSVP: 3 reserved flows, one
refused at C1→C2, state tables filled in both domains; DiffServ: EF/AF41/AF42/BE packets mid-path, per-class
queues, boundary set to *bleach* so the print shows an EF packet arriving in B's BE queue), no controls. The slides therefore do **not** use `export-skip`.

### Visual rules

Colours: green family for EF/reservations, the FEI cyan only for fills/marks (never text), AF in green tints by drop
precedence (lighter = higher drop precedence) or EKF blue for the AF class (builder's call, must be ≥3:1 on both
backgrounds), best effort in muted grey, drops/refusals FMT red. Labels ≥ 14 px inside the component (the repo's
components use 10–14 px; 14 px is the floor here), title text 18 px. *(Builder-check call.)* Rounded corners follow
VSB-STYLE R24. Every colour through CSS variables so `d` (dark) works; check both themes before committing.
